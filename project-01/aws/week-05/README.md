# Core Concepts

## Metrics

Metrics are numerical measurements collected over time.

Examples:

```text
CPUUtilization
Memory usage
Disk usage
NetworkIn
NetworkOut
DatabaseConnections
FreeStorageSpace
ReadLatency
WriteLatency
```

Metrics help answer:

> "How is the system performing?"

---

## Logs

Logs contain detailed events generated by systems and applications.

Examples:

```text
Linux system logs
Authentication events
Docker errors
Application errors
Database connection errors
Service failures
```

Logs help answer:

> "What happened?"

---

## Alarms

CloudWatch alarms watch metrics and trigger when a condition is met.

Example:

```text
EC2 CPUUtilization > 80% for 5 minutes
```

or:

```text
RDS FreeStorageSpace drops below a threshold
```

Alarms help answer:

> "When should someone investigate?"

# Task 3 — Understand Default EC2 Monitoring

EC2 automatically publishes several metrics to CloudWatch.

However, some operating system metrics are not available by default.

For example:

```text
Memory usage
Disk filesystem usage
```

To collect those, you will configure the:

```text
Amazon CloudWatch Agent
```

---

# Task 4 — Configure CloudWatch Agent

Install and configure the CloudWatch Agent on your EC2 instance.

Conceptually:

```text
EC2 Instance
     |
     v
CloudWatch Agent
     |
     v
CloudWatch
```

The CloudWatch Agent can collect:

```text
Memory usage
Disk usage
Additional system metrics
Linux logs
```

You may configure the agent manually for the lab.

Terraform is encouraged for AWS-side resources where practical.

---

# Task 5 — IAM Permissions for CloudWatch Agent

The EC2 instance needs permission to send metrics and logs to CloudWatch.

Use an IAM role attached to the EC2 instance.

Conceptually:

```text
EC2
 |
 v
IAM Role
 |
 v
Permission to publish
metrics and logs
 |
 v
CloudWatch
```

Do not hardcode AWS access keys onto the EC2 instance.

Use IAM roles instead.

# Troubleshooting Exercise

Work through this scenario:

> A user reports that Memos is no longer loading.

Do not immediately start changing infrastructure.

Troubleshoot the system layer by layer.

---

## Step 1 — Check EC2

Is the instance running?

Check:

```text
EC2 instance state
EC2 status checks
CPU
Network
```

---

## Step 2 — Check Docker

SSH into the instance.

Run:

```bash
docker ps
```

If Memos is not running:

```bash
docker ps -a
```

Check logs:

```bash
docker logs memos
```

---

## Step 3 — Check the Application Port

Verify that the application is listening.

```bash
ss -tulpn
```

Look for the expected Memos port.

Example:

```text
5230
```

---

## Step 4 — Check Security Groups

Verify that the EC2 Security Group allows the required inbound application traffic.

Also verify that SSH rules are correct.

---

## Step 5 — Check Database Connectivity

From the EC2 instance:

```bash
nc -vz RDS_ENDPOINT 5432
```

If that fails, investigate:

```text
Security Groups
RDS status
DNS
Network routing
Database port
```

---

## Step 6 — Test PostgreSQL

Use `psql` to test database authentication.

Example:

```bash
psql \
  --host=RDS_ENDPOINT \
  --username=DB_USERNAME \
  --dbname=memos
```

A successful TCP connection does not automatically mean database authentication works.

---

## Step 7 — Review CloudWatch

Check:

```text
EC2 metrics
CloudWatch Logs
CloudWatch Agent metrics
RDS metrics
CloudWatch alarms
```

Use the monitoring data to determine whether the issue is:

```text
Compute
Application
Network
Database
```

# Cost Awareness

Monitoring resources can create additional AWS charges.

Pay attention to:

```text
CloudWatch log ingestion
Log storage
Custom metrics
SNS usage
EC2 runtime
RDS runtime
Data transfer
```

For the lab:

- Keep log retention reasonable
- Avoid collecting unnecessary logs
- Avoid creating excessive custom metrics
- Stop or remove resources you no longer need
